Low-level design · Draft v1

Concert & festival lineup → Spotify playlist

A user picks an upcoming concert or festival, mostly in India. The app turns its lineup into a playlist in the user's Spotify account. This draft merges three research passes: web app architecture, event data sources, and the Spotify API as of November 2026.

21 Nov 2026 MVP: 4 weeks · ≤5 users TypeScript · Postgres · $0 hosting

0Hard constraints

These four facts drive most of the decisions below.

Spotify caps new apps at 5 users

Development Mode allows 5 allow-listed users, and the owner needs Premium. Extended Quota needs a registered business with about 250k monthly users. (quota modes, criteria)

The MVP is a closed beta. A public launch needs a product decision (§15).

Top tracks and popularity are gone

New apps lost /artists/{id}/top-tracks, batch gets, and the popularity and followers fields. Search is capped at limit=10. Use POST /me/playlists and /playlists/{id}/items. (Feb 2026 changelog)

We build our own "top tracks" list from search (§7).

No API covers Indian lineups

BookMyShow and District have no public API and restrict scraping. Instagram and Facebook collection breaches Meta Terms §3.2.3. Ticketmaster doesn't operate in India.

For India, admins enter events and users can submit lineups. Nothing is scraped.

Spotify blocks can last hours

Developers report Retry-After values of up to about 19 hours, and calling during a block reportedly extends it. The quota is shared across the whole developer account.

One shared throttle. Long blocks pause the job and resume it later (§8).

Hosting must cost $0

The app is free, so every piece has to fit in a free tier. That rules out always-on worker processes and a separate Redis server. One cost remains: the Spotify app owner needs a Premium subscription.

Serverless web app, Postgres as the job queue, scheduled jobs on GitHub Actions (§2).

2Architecture

One repo, no servers to keep running, and $0 a month. The web app runs on Vercel's free plan, the database is Neon's free Postgres, and scheduled jobs run on free GitHub Actions. There is no Redis and no always-on worker: Postgres holds the job queue and the Spotify pause flag.

  • Playlist jobs run in short steps. Serverless functions can't run for minutes, so the browser calls POST /api/playlist-jobs/:id/step every ~1.5 seconds while the page is open. Each call does up to ~8 seconds of work, saves a checkpoint, and returns progress. A short lease (locked_until) stops two steps running at once. If the user closes the tab, the job continues when they come back, or the next scheduled sweep finishes it.
  • Background work runs on a schedule. Event sync, artist matching and re-checks run as Node scripts in GitHub Actions and write straight to Postgres. They're free and unlimited for a public repo; a private repo gets 2,000 minutes a month, and a daily 5-minute run uses about 150.
  • Every Spotify call goes through one SpotifyClient whose pause flag lives in Postgres, because the quota is counted per developer account.
  • Artists are matched to Spotify when the event comes in, not when someone generates a playlist. A cached festival then costs about 80 track searches plus 6 write calls instead of about 180.

Deduplication

  • Candidates: events with the same country and city whose start dates are within a day of each other.
  • Score: 0.4 × venue similarity (Jaro-Winkler after alias lookup) + 0.3 × event-name token overlap (year and edition removed) + 0.3 × overlap of matched artists (Jaccard).
  • Decision: at 0.85 or above, merge automatically. Between 0.6 and 0.85, send to the admin queue.
  • When sources disagree: admin beats JamBase, which beats Ticketmaster, which beats a user submission.
  • Lineup changes: recompute lineup_hash. A change marks existing playlists as stale.

6Artist matching

The artist-resolve job uses an app token (client credentials) and goes through the same rate gate at low priority.

  1. Normalize the name: NFKD, strip diacritics, casefold, and map &/and/+ to one form. Strip a leading "the" or "DJ ", and suffixes like "(live)", "(DJ set)", "[hybrid]".
  2. Split b2b and vs entries into separate artists. Split on & only if the full name doesn't match, because many bands have "&" in their name.
  3. Check artist_aliases first. If the name is there, stop.
  4. Search type=artist&limit=10 twice: once with q=artist:"<raw>" and once with the normalized name.
  5. Score each candidate (popularity is no longer available):
SignalPoints
Exact match after normalizing+50
Differs only in accents+30
Matches after removing "DJ"+25
Search position (rank 0 is the top result)up to +15, as 15 − 1.5 × rank
Has images+10
Genre overlaps the event's genre unverified+10
MusicBrainz links to the same Spotify artist (phase 3)+20

Decision: accept automatically if the top score is at least 70 and beats the runner-up by at least 15. Otherwise mark it needs_review, and the admin picks from the top 3 with images and albums. Always send for review: names of 3 characters or fewer, common words, and names shared by several artists.

Track selection

  • Hits mode (MVP):
    • Search type=track&q=artist:"<exact name>"&limit=10&market=<user.market>.
    • Keep only tracks whose artists[] includes the matched Spotify artist ID.
    • If that gives too few, take the first tracks of the newest albums and singles.
    • unverified Whether search results come back roughly in popularity order. Test this on day 1.
  • Setlist mode (phase 2):
    • Count how often each song appears in the artist's recent setlists on setlist.fm.
    • Search track:"<song>" artist:"<name>", prefer studio versions over live or karaoke ones, and match on artist ID plus title.
    • Requires a commercial agreement with setlist.fm once the app makes money.
  • Dedupe by track ID, then ISRC (external_ids.isrc, restored in March 2026), then title + artist.
  • Cache each artist's track picks in artist_track_cache for 7 days.

Job lifecycle

stateDiagram-v2
  [*] --> queued
  queued --> running
  running --> succeeded
  running --> partial: some artists unmatched
  running --> paused: long 429 / quota exceeded
  paused --> running: resume_after passed
  running --> failed: Spotify login expired
  • A running job moves through the stages resolve → select → create → add → cover, a few calls per /step request.
  • Each step claims the job with UPDATE … SET locked_until = now() + 15s WHERE id = $1 AND (locked_until IS NULL OR locked_until < now()). If no row comes back, another step is already running and this one just returns progress.
  • checkpoint stores {selectedTrackIds, playlistId, chunksDone}, so a resumed job never repeats work.
  • The Spotify playlist ID is saved right after POST /me/playlists, before any tracks are added.
  • Tracks are added in chunks of 100 via POST /playlists/{id}/items, saving progress after each chunk. When updating an existing playlist, the first chunk uses PUT to replace its contents.

8Spotify client layer

Tokens

  • Reuse the stored access token while it has more than 60 seconds left.
  • Otherwise lock on the user (Postgres advisory lock), refresh it, and save any new refresh token Spotify returns.
  • If Spotify answers invalid_grant, mark the user as needing to reconnect and fail the job with a "Reconnect Spotify" message.
  • Access tokens last 1 hour. Refresh tokens expire 6 months after issue, and refreshing doesn't extend them.
  • Scopes: playlist-modify-private and playlist-modify-public, plus ugc-image-upload once covers ship.

Rate gate: the only path to Spotify

async function call(req, { priority }) {
  const pausedUntil = await gate.pausedUntil();   // spotify_gate row, cached ~2s per instance
  if (pausedUntil > now) throw new SpotifyPaused(pausedUntil);   // step returns; browser retries later
  await bucket.take();      // ~2–3 req/s, max 3 in flight per step (tunable; Spotify publishes no numbers)
  const r = await fetch(req);
  if (r.status === 429) {
    const body = await r.json().catch(() => ({}));
    const ra = parseRetryAfter(r.headers.get('Retry-After'));  // seconds or HTTP-date; NaN-safe
    if (body?.error?.reason === 'QUOTA_EXCEEDED' || (ra ?? 0) > 120)
      throw new SpotifyBlocked(ra);          // job → paused(resume_after); no retry
    await setMaxPausedUntil(now + (ra ?? fullJitter(attempt, 1, 60)) + rand(0, 0.5));
    return retry();                          // ≤5 attempts
  }
  if (r.status >= 500) return retryWithFullJitter();
  return r;
}
  • setMaxPausedUntil is one SQL statement, UPDATE spotify_gate SET paused_until = GREATEST(paused_until, $1), so the later deadline always wins.
  • No calls go out during a pause, because developers report that calling during a block extends it.
  • Playlists users are waiting for run before background ingest and matching work.

Idempotency

  • POST /api/playlist-jobs requires an Idempotency-Key header, so a double-click starts only one job.
  • If a playlist already exists for the same user, event and options, the UI offers "Update existing" instead of creating a duplicate.

12Security & compliance

  • Spotify tokens are encrypted with AES-256-GCM, with a key version so keys can rotate. They never reach the browser.
  • Session cookie: httpOnly, Secure, SameSite=Lax, holding a random ID that is stored hashed.
  • The GitHub Actions jobs get only the secrets they need (database URL for a restricted role, Spotify client ID and secret). They never get the token encryption key, so they can't read user tokens; the playlist sweep, which does need it, runs as a separate workflow.
  • Every external payload is validated with Zod. Raw HTML from outside is never rendered.
  • Spotify Policy: no app about a single artist (II.1), credit Spotify (II.4), no machine learning on Spotify content (III.13–14), easy disconnect (I.1.2).
  • unverified Whether Policy III.5, which bans products "integrated with content from another service", covers setlist.fm data. Check before shipping setlist mode.
  • Redirect URIs must use HTTPS. For local development use http://127.0.0.1:3000/api/auth/spotify/callback, because localhost is rejected.

14Testing

  • Unit tests: name normalization and B2B splitting; match scoring (table-driven, with Indian names and DJ aliases); dedupe scoring; parseRetryAfter with seconds, a date, garbage and a missing header.
  • Rate gate: a fake Spotify server returns 429 with Retry-After: 2, Retry-After: 5000, and a QUOTA_EXCEEDED body. Check that all workers pause together, nothing is sent during the pause, and the job ends up paused.
  • Resume: abort a step partway through adding tracks, and fire two steps at once. Check there's no duplicate playlist and no duplicate tracks.
  • Day-1 check against the real API: are search results roughly in popularity order, and is genres filled in for Development Mode apps?

15Risks & open decisions

Decision needed before a public launch: with Spotify's 5-user cap, choose between a personal or invite-only tool; users bringing their own Spotify developer credentials (whether Spotify's terms allow this is unverified); a public track-list page where only invited users can save to Spotify; or adding Apple Music, which has an official way to create playlists.
